Why I Chose a Static Site

October 8, 2026 architecture static-sites

After exploring various blogging platforms, I decided to build my own static site. No databases, no server-side rendering, no complex build pipelines — just files that work everywhere. Here's why this approach works for me.

What Is a Static Site?

A static site consists of pre-built HTML, CSS, and JavaScript files served directly to the browser. There's no server-side processing, no database queries, no dynamic rendering on each request. The files are generated once (at build time) and served identically to every visitor.

The Alternatives I Considered

Platform Pros Cons
WordPress Feature-rich, huge ecosystem, easy for non-technical users PHP/MySQL required, security concerns, performance overhead, frequent updates
Ghost Modern, fast, great writing experience Node.js server required, paid hosting or self-hosting complexity
Medium Zero setup, built-in audience, beautiful editor No ownership, paywall issues, limited customization, platform risk
Jekyll/Hugo Static output, mature, GitHub Pages native Ruby/Go dependency, build step, template learning curve
Next.js/Astro Modern, powerful, great DX Complex build pipeline, overkill for simple blogs, JS fatigue

Why Plain Static Files Won

1. Zero Dependencies

No package.json, no node_modules, no build tools, no version conflicts. The site is the source code. I can open index.html in any browser and it works.

2. True Ownership

My content lives in plain HTML files in a git repository. No vendor lock-in, no export hassles, no API changes breaking my content. If GitHub Pages disappears, I push to Netlify, Vercel, or any static host in minutes.

3. Performance by Default

Static files served from a global CDN (like GitHub Pages, Cloudflare, Netlify) are as fast as it gets. No server cold starts, no database queries, no rendering time. First Contentful Paint is essentially network latency.

4. Security Simplicity

No server-side code means no injection vulnerabilities, no authentication bypasses, no CMS exploits. The attack surface is essentially "serve static files" — a solved problem.

5. Cost: Free

GitHub Pages, Netlify, Vercel, Cloudflare Pages, GitLab Pages — all offer generous free tiers for static sites. No server costs, no database costs, no bandwidth worries for a personal blog.

6. Longevity

HTML is the web's native format. The first website from 1991 still renders today. My blog posts will be readable in 20 years without migration, without a compatible runtime, without a specific platform existing.

The Trade-offs

It's not all perfect. Here's what I give up:

  • Dynamic features: No comments (use Webmentions or a third-party service), no search (use Algolia or static search), no user accounts
  • Content editing: No visual editor — I write HTML directly (or Markdown with a simple parser)
  • Collaboration: Non-technical contributors need git/HTML knowledge
  • Scale: Not suitable for thousands of pages without a build step (but I won't have thousands of posts)

My Setup

For this blog, I keep it intentionally simple:

blog/
├── index.html          # Homepage with post list
├── about.html          # About page
├── projects.html       # Projects showcase
├── styles.css          # All styles
├── script.js           # Minimal JS (dark mode, etc.)
└── posts/
    ├── first-post.html
    ├── learning-html-css.html
    └── static-site-generators.html

Adding a New Post

  1. Create a new .html file in posts/
  2. Follow the existing article template
  3. Add a link to it on index.html
  4. Commit and push — live in seconds

When I'd Reconsider

If my needs change, I'd look at:

  • Astro: If I want component-based authoring with static output
  • 11ty: If I want a build step for templating but static output
  • Ghost: If I need a proper CMS for a team

But for now? Static files, git, and a CDN. Simple, fast, and mine.
